What changed in v2, and what is being reviewed
  1. Requested addition: the Operator asked for key controls on a connected computer’s page (design v7; consolidated in v8). Choose Computer page to see Build Mac’s Settings and its join keys, reached through the already-connected Home Hub. Settings at the computer remains the other entry.
  2. Named keys: the design now calls these request keys and provides keys create <name>. The form asks for a key name, replacing v1’s Hub-address field. Use one named key for each self-hosted Hub; its actual Hub origin and access are reviewed on the Needs-you card.
  3. Shown once: the secret appears only in the creation response. The list retains the name, creation time and last use, never a reveal action. Copy it into the named self-hosted Hub’s Add computer. Hosted Coral Hub receives no key.
  4. Through Home Hub: creating/revoking requires an owner device with Interact or Launch. The signed response returns the key once to this browser; Home Hub’s relay sees it in transit, as the design states. The view-access example shows no key list or management controls.
  5. Limits through a Hub: three live keys and ten creations per hour per connected link. The limit example blocks creation and keeps Revoke available. Local Settings does not claim these per-link limits apply to the local caller.
  6. Revoke: names the key and computer, confirms before ending it, and leaves existing Hub connections in place. A failure keeps the key active and offers retry.
  7. Build boundary: local key routes belong to the first build. Signed remote creation/revocation is a later commit, initially shut behind its gate. This mock shows the requested finished interaction; it does not turn that gate on.
  8. Backend contract determines exact validations and retry wording. This file replaces the token mock at the Operator/Orchestrator’s explicit request; the separately approved Needs-you request mock is unchanged.
