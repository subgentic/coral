# Goals folder request plan (#22040)

The expanded Goals ledger must show every task, its actual state, and the review documents/questions belonging to it. The goal rollup supplies counts, not task records, so the existing board Tasks View endpoint supplies the rows.

On opening a goal: GET /api/board/{team}/tasks?goal={positive-id}&limit=200. Follow next_cursor using cursor until exhausted; deduplicate task IDs and reject repeated cursors. Cost is one task read per open goal up to200 tasks, otherwise ceil(task-count/200) pages. It does not read task details. Reads use the existing qualified board transport through the goal reader and a shared concurrency limit of3.

Review files use the existing artifacts endpoint with goal, repeated review-history tag filters, versions=newest, sort=name, limit=50 and explicit Load more pagination. Open questions use the existing source-qualified Operator questions list. Under #22102, answered questions use GET /api/operator-asks?board={team}&goal={positive-id}&state=answered&limit=100, following next_cursor until exhausted with ID deduplication and repeated-cursor refusal. This is one read per expanded goal per 100 answered questions, within the same concurrency limit and 30-second cache; folded goals never read. The additive query is routed through serverFetch for the team’s computer, preserving owner-only refusal. Rows use explicit task_id and goal_id; missing answer text is never synthesized.

Folded cards read nothing, including when visible or previously loaded: both observer loads and poll/event refreshes are gated by current expansion. The first two goals start expanded; other cards wait for expansion. Open-goal results are cached30seconds, with review-change invalidation; normal background refresh runs every30seconds only while the mounted ledger is visible. Closing a card during an in-flight read does not cancel requests already dispatched.

The answered-question read additionally registers board, goal, state, limit and cursor on the existing operator-asks route. The task read adds goal, limit and cursor keys on the existing board Tasks route to the cloud Inbox folder plan. The fixed Chats/Board baseline and all cloud route authorization remain unchanged. The census checks positive goal IDs and limit200. No additional Hub route or write is introduced.

Under #22102 the first State-menu open also reads the existing all-state goal inventory for all six menu counts, including Done/Dropped. Those counts are cached60seconds and invalidated on the goal change counter. The menu keeps an ellipsis on refusal rather than inventing a zero; the list's selected state remains unchanged. This reuses the existing state=all goal read and owner-qualified transport, without task or artifact reads for folded goals.
